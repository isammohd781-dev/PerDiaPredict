# Restricted disclosure setup

## What this update protects

The administrator Reports and Activity screens deny access until all of these match:

- An independent custodial password, separate from ADMIN_PASSWORD, at least 16 characters.
- Exact patient ID/email for individual or listed-group permits; current care country for every permit. Country-wide scope must be explicitly enabled by the custodian. See GROUP_ACCESS_SETUP.md.
- A pre-registered permit with `medical_approved = true`, an approver, requesting authority, request reference and purpose.
- A permit scope (`reports` or `activity`) and a timezone-aware expiration time.

The administrator cannot create permits from this dashboard. Typing a permit reference or checking a declaration is insufficient. The custodian must verify documents outside the application and register the decision in private deployment configuration. The software does not verify government identities, medical licensing, signatures or legal validity of requests.

Access lasts at most five minutes. Individual access locks when changing sections; group access may cover both Reports and Activity, but locks when leaving those sections. Access is checked again before reading records or preparing an export. Removing/changing a permit or credential invalidates grants when the running app reads the updated policy; restart after editing Streamlit Secrets. Five failed verification attempts lock that section for ten minutes in SQLite, across browser sessions. This shared gate can be locked by another person's failed attempts.

Reports exposes only completed records for the selected account and patient ID. It no longer offers a bulk Excel download or deletion from the administrator Reports screen. Legacy unverified Excel rows are excluded.

Activity: choose current care country, then a patient. After verification, only that patient's account ID and exact email-linked care/disclosure events are shown. Prepare all recorded activity PDF creates a PDF with permit and request metadata, actor identifiers and recorded events. Export preparation is logged as preparation, not proof that a file was downloaded or received. Patient-side download requests are logged separately.

## Local test configuration

1. Retain your project files, accounts and databases. Add `disclosure_access.py` and replace `admin_dashboard.py` and `diabetes_app.py` from this package.
2. Merge the example keys from `disclosure_secrets.example.toml` into a private `.streamlit/secrets.toml`. Never upload the actual secrets file, patient data or databases to public GitHub.
3. Set a long, unique DISCLOSURE_PASSWORD locally. No working password is shipped in this package.
4. For a software test, an authorized tester can register a permit for a synthetic patient. Use their exact patient ID, email and current country. Mark it explicitly as a synthetic test in `authority`, `request_reference`, `approved_by`, and `purpose`. Set `medical_approved` to true only for that authorized synthetic test, and set a short future UTC expiration. This test flag is not medical approval for real data.
5. Restart the application. Select the patient in Reports or Activity and enter the custodial password and permit reference.

Alternative server settings: `PERDIA_DISCLOSURE_PASSWORD` and `PERDIA_DISCLOSURE_PERMITS_JSON` (a JSON array with the same fields). There is no fallback to the administrator password.

## Important boundary

This is application-level access control in a local development prototype. It cannot protect data from a person who owns the computer, code, configuration or database files. Stored data is not encrypted by this patch. Ordinary administrator UI password-reset, full account backup export and restore controls have been removed to close an indirect portal-access path. The code still contains low-level account recovery functions for future custodial tooling; code/files owners can invoke or change them. The administrator directory exposes limited account metadata, not health answers. This is not a complete separation from local machine owners.

To protect data even from an application administrator, deploy a separate custodial backend with individually authenticated roles, restricted account recovery, encrypted storage/backups, keys managed by a different authority, and independently retained audit logs. The application server's filesystem and deployment configuration must not be accessible to the restricted administrator. This is a separate production architecture, not something a local password form can provide.

The five-minute grant governs new application reads/export generation; it cannot revoke PDFs already issued, media URLs already generated by Streamlit, screenshots or previously downloaded files. This update is not a compliance certification or a legal/medical authorization.

Activity is limited to recorded events. Historical actions that were never logged cannot be reconstructed. New events include page navigation, report opening/view changes, report download requests and logout, alongside existing login, prediction and care-team actions. Timestamps are shown as stored; sorting uses the server's local timezone for older timestamps without a timezone.
